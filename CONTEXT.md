### Текстуры

Движок берёт материалы из LabPBR-пака, если он распакован в `public/pack/`, и
дополняет процедурными там, где пак их не даёт (вода и лава). Без пака работает
целиком на процедурных.

```bash
node scripts/extract-pack.mjs            # найдёт .zip в корне сам
node scripts/extract-pack.mjs "Pack.zip" public/pack
```

Соответствие наших имён именам в паке — `scripts/pack-mapping.json`.
Скрипт печатает, чего в паке не нашлось.

### Запуск

```bash
npm install
npx vite --port 5173 --strictPort     # dev-сервер
npm run build                          # проверка типов + продакшн-сборка
npx tsc --noEmit                       # только проверка типов
```

`npm run dev` тоже работает, но при передаче аргументов через `npm run dev --
--port` npm их коверкает — надёжнее вызывать `npx vite` напрямую.

### Проверить, что ничего не сломано

```bash
node scripts/smoke.mjs "http://127.0.0.1:5173/?seed=424242"
```

Смоук-тест компилирует **все** шейдеры и рисует кадр. Проверка типов внутрь
GLSL не смотрит, поэтому это единственный способ узнать, что шейдеры живы.
Ошибка компиляции печатается вместе с фрагментом собранного исходника вокруг
проблемной строки.

### Замерить производительность

```bash
node scripts/gputime.mjs "http://127.0.0.1:5173/?seed=424242" medium 18
```

Читать GPU-миллисекунды по проходам, а не FPS: FPS на этом ноутбуке гуляет
примерно в 1.5 раза между холодным и прогретым состоянием (см. 6.1).

### Текущее состояние

Движок рабочий и играбельный. Средний пресет: 58 fps по медиане, 53 по
среднему (после LOD, пропуска теней на отвёрнутых гранях и условной копии
кадра). Есть LOD, LabPBR-паки и параллакс с самозатенением. Один нерешённый
визуальный артефакт, но теперь с измеренной локализацией (раздел 9). Незакрытые
крупные фичи: occlusion culling, воксельное GI, звук, сохранение мира.

## 1. Исходная задача

### Что просил заказчик

Дословная постановка была такой:

> Хочу чтоб ты пересоздал майнкрафт заново. Меня напрягает то что майнкрафт
> плохого качества, а то что на ютубе снимают как лютое качество — это
> достигается только костыльными подключениями шейдеров.

И расширенно:

> Можно ли сделать свой собственный майнкрафт, но чтоб качество было ультра
> высоким и при этом без того чтоб эта игра потребляла как средняя нейронка?
> Я понимаю что есть всякие шейдеры и их можно установить, но на мой взгляд
> шейдеры — это костыль (поправь если ошибаюсь) и они прибавляют невероятный
> вес самой игре, и вот нельзя ли саму игру с нуля создать такой живописной и
> реалистичной, чтоб закаты и дожди и облака и всё было люто реалистичным
> вплоть до травы? Ведь есть же условный left4dead который по качеству очень
> детализован и при этом на нём можно играть на средних рабочих компах типа
> lenovo thinkpad t480.

### Референсы

Приложены четыре скриншота Minecraft с шейдер-паками (SEUS и подобные):

* `1588341810-1-1.jpg` — рассвет над водой в хвойном лесу: солнце низко над
  горизонтом, длинная солнечная дорожка по воде, объёмные лучи между деревьями,
  bloom вокруг солнца, густая трава на переднем плане, блик-артефакты объектива.
* `resize_1500_833_true_q90_878522_...jpeg`
* `f0c17375c5_infinity-visuals-shader-3.webp`
* `best-minecraft-shaders-seus.avif`

Общий знаменатель референсов, который и стал техническим заданием: **низкое
солнце, физически достоверное небо, вода с отражениями и бликом, объёмная
дымка, плотная трава, мягкие тени**.

### Мнения, которые заказчик уже собрал

**Gemini** предлагал: писать нативный рендер на Vulkan/DirectX 12/WebGPU;
заложить PBR прямо в структуру данных блоков; мешить чанки на GPU через compute
shaders; небо считать аналитически (Bruneton или Hosek-Wilkie) вместо
рейтрейсинга; туман и отражения делать в экранном пространстве; траву — через
GPU-инстансинг с LOD и колыханием в вершинном шейдере. Приводил в пример
Vintage Story.

**ChatGPT** предлагал: C++ + SDL3 + bgfx либо Godot 4 с собственным воксельным
рендером; давал схему архитектуры (World → Chunk Manager → Mesh Builder →
LOD/Culling → Renderer → Post Processing); настаивал на greedy meshing, face
culling, chunk LOD, frustum/occlusion culling и агрессивном стриминге; главный
принцип формулировал как «GPU никогда не должен знать о миллионах блоков».

### Что из этого правда

Заказчик просил поправить его, если он ошибается насчёт шейдеров. Поправка
такая: **шейдеры — не костыль сами по себе, вся современная графика это
шейдеры.** Костыль — это конкретно шейдер-паки для Minecraft, и по конкретной
причине: OptiFine/Iris перехватывают вызовы рендера игры, спроектированной под
фиксированный конвейер OpenGL 2.x, и достраивают поверх неё G-буфер, тени и
пост-обработку. Движок при этом ничего о них не знает — он по-прежнему шлёт
геометрию так, как удобно ему, а не рендеру. Отсюда и вес, и падение
производительности.

Вывод, который лёг в основу проекта: то же самое качество, будучи **свойством
самого движка**, стоит в разы дешевле. Это и было проверено.

Сравнение с Left 4 Dead 2 тоже точное, но по другой причине, чем кажется: там
статичная геометрия с запечённым светом и предпосчитанной видимостью, а
воксельный мир генерирует геометрию на лету. Поэтому решения оттуда напрямую не
переносятся — нужны свои.

## 2. Выбор стека

Прежде чем что-то решать, я проверил машину. Это оказалось решающим.

```
cl, g++, gcc, clang, cmake, ninja, cargo, rustc, dotnet, msbuild  →  НЕТ
node v22.16.0, npm 11.6.0, python 3.11.9, git                     →  есть
Chrome и Edge                                                      →  есть

GPU: Intel(R) UHD Graphics 620
CPU: Intel Core i5-8350U, 4 ядра / 8 потоков
RAM: 12 ГБ
ОС:  Windows 11 Pro
```

Два вывода:

1. **Целевое железо — это сама машина разработки.** i5-8350U + UHD 620 это
   ровно тот класс, что и ThinkPad T480 из постановки. Значит любой замер
   производительности сразу честный, без экстраполяции.
2. **Ни одного компилятора C/C++/Rust/.NET в системе нет.** Поставить MSVC
   Build Tools — это около 7 ГБ и права администратора.

### Почему не C++

Соблазн был: и Gemini, и ChatGPT советовали нативный движок. Но узкое место
здесь — **не язык хоста, а UHD 620**: 24 исполнительных блока, порядка
400 GFLOPS, память общая с процессором, около 25–35 ГБ/с на всё.

Разложим, где вообще тратится время в воксельном движке:

| Работа | Где выполняется | Зависит от языка? |
|---|---|---|
| Меширование чанка | CPU, 1–3 мс на секцию на typed arrays | слабо |
| Генерация шума | CPU, вынесена на решётку | слабо |
| Растеризация, шейдинг, тени | GPU целиком | нет |
| Заполнение буферов вершин | шина памяти | нет |

Практика это подтвердила: финальный профиль показывает 24 мс GPU против 23 мс
CPU, причём CPU занят **накладными расходами драйвера на draw call**, а не
логикой на JavaScript (генерация мира, поиск блока лучом и сбор источников
света суммарно дают 0.25 мс на кадр). На C++ эти 23 мс стали бы, может, 18 —
но не 2.

### Что выбрано

**TypeScript + WebGL2 + Web Workers, свой рендерер без three.js.**

* WebGL2 = OpenGL ES 3.0: MRT, float-текстуры, 3D-текстуры, массивы текстур,
  инстансинг, uniform buffer objects, transform feedback. Всего, что нужно для
  задуманного пайплайна, хватает.
* Нет compute shaders — но меширование на CPU в воркерах это и так стандартная
  практика, а не компромисс.
* three.js не взят сознательно: он навязывает свою модель материалов и
  проходов, и кастомный кадровый граф пришлось бы прошивать против неё.
* Ноль зависимостей в рантайме. Своя математика (200 строк) вместо gl-matrix —
  чтобы контролировать раскладку матриц под UBO.

Сборка: Vite. Итог — **79 КБ gzip на всю игру**, потому что ассетов нет вообще.

## 3. Ключевые архитектурные решения

### 3.1 Размер чанка: 32×32×192, а не 16×16×256

Minecraft использует 16×16. Здесь 32×32, и это решение принято ради
**накладных расходов драйвера**: на интегрированной графике через ANGLE→D3D11
каждый draw call стоит десятки микросекунд, поэтому меньше и крупнее выгоднее,
даже ценой более дорогого перестроения меша при правке блока.

Высота 192 вместо 256: рельеф упирается в ~186, море на 62. Ничего не теряется,
а каждая колонка стоит на 25% меньше памяти и на 25% меньше времени заливки
света.

Одна колонка — одна аллокация буфера с фиксированной раскладкой (блоки, свет,
биом, два тинта, две карты высот). Это позволяет отдать воркеру один хендл.

### 3.2 Глобальная решётка генерации

Самое важное решение в генераторе. Низкочастотные поля (континентальность,
эрозия, хребты, «странность», температура, влажность, реки) считаются **не в
координатах чанка, а на глобальной решётке с шагом 4 блока** и билинейно
интерполируются.

Зачем: дерево, посаженное из соседнего чанка, должно встать ровно на ту землю,
которую этот чанк сгенерирует. При попиксельном или почанковом расчёте высоты
неизбежно расходятся на доли блока, и деревья висят в воздухе или тонут. С
глобальной решёткой любой чанк, касающийся узла решётки, получает для него
**идентичное** значение.

Высокочастотная детализация считается на полном разрешении — именно её глаз
читает как фактуру рельефа.

Деревья генерируются из блока 3×3 соседних чанков и обрезаются по границам
целевого. Никаких записей в соседние чанки, полная детерминированность.

### 3.3 Строгий порядок зависимостей

```
generate  →  без зависимостей
light     →  окрестность 3×3 сгенерирована
mesh      →  окрестность 3×3 освещена
```

Это то, что позволяет строить меш **сразу правильно**. Альтернатива — мешить
как только можно и переделывать при появлении соседей — даёт видимые швы и
лишнюю работу. Цена: колонки грузятся на два кольца шире дальности прорисовки,
и мешится только внутренняя область.

### 3.4 SharedArrayBuffer

Данные мира лежат в разделяемой памяти, воркеры читают соседние чанки напрямую.
Без этого пришлось бы на каждое задание копировать «юбку» из соседей — а для
корректной заливки света она нужна шириной в несколько блоков.

Требует cross-origin isolation, поэтому dev-сервер отдаёт заголовки COOP/COEP
(прописано в `vite.config.ts`). Если изоляции нет (например, `dist` открыт через
`file://`), движок прозрачно переключается на однопоточный конвейер с бюджетом
времени на кадр — **тот же код, другой планировщик**. Ради этого стадии
вынесены в `world/pipeline.ts` как чистые функции над хранилищем.

### 3.5 Формат вершины: 12 байт

```
offset 0  : 3 × uint16  позиция в восьмых долях блока, со смещением в 1 блок
offset 6  : 2 × uint8   тайловые UV
offset 8  : 1 × uint32  упакованные: слой текстуры, грань, AO, небесный свет,
                        блочный свет, режим тинта, флаг ветра
```

Индексный буфер **один на весь мир**: мешер всегда пишет по 4 вершины на квад,
поэтому паттерн `0,1,2, 0,2,3` статичен. Это убирает одну загрузку и один bind
на каждую секцию.

Смещение позиции в 1 блок — не косметика. Крестовидное растение на краю секции
законно выходит за её пределы примерно на 0.6 блока, и без смещения координата
уходила в минус, заворачивалась в 65535 и улетала на 8192 блока (см. раздел 5).

### 3.6 Reversed-Z

Проекция бесконечная с обратной глубиной: ближняя плоскость → 1, бесконечность
→ 0, тест `GEQUAL`, очистка нулём. Это распределяет точность float по всей
дальности вместо концентрации у камеры. Соглашение сквозное — тени тоже
рендерятся в обратной глубине, чтобы не держать в голове два правила.

### 3.7 Форвардный рендер, а не отложенный

Отложенный рендер требует толстого G-буфера, а трафик кадрового буфера — ровно
то, чего интегрированная графика позволить не может. Форвардный проход с
сортировкой непрозрачной геометрии от ближнего к дальнему даёт раннее
отсечение по глубине почти бесплатно.

Изначально был ещё depth prepass — и его пришлось убрать, см. раздел 6.

### 3.8 Процедурные материалы

46 материалов генерируются при запуске в два массива текстур (альбедо + нормаль
/шероховатость/AO). При 128 px это около 6 МБ видеопамяти против сотен мегабайт
у сопоставимого ресурс-пака, и уровень детали становится настройкой, а не
другой загрузкой.

Альбедо хранится в `SRGB8_ALPHA8`, чтобы GPU линеаризовал его бесплатно при
выборке; карта поверхности — в линейном `RGBA8`, потому что там векторы, а не
цвета.

### 3.9 Атмосфера как единственный источник цвета

Реализована модель Hillaire 2020:

* LUT трансмиттанса 256×64 — один раз при запуске;
* LUT многократного рассеяния 32×32 — один раз при запуске;
* sky-view LUT 192×108 — каждый кадр.

И дальше **всё** читает эту одну маленькую текстуру: купол неба, цвет тумана,
ambient на каждой грани блока, отражение в воде, подсветка облаков, цвет
дождевых струй. Поэтому сцена автоматически согласована: закат не нужно
«подкрашивать», он приходит в туман и в воду сам.

Ключевой момент, из-за которого это работает: цвет тумана — это **реальная
яркость неба в направлении взгляда**, взятая из LUT. Дымка перед солнцем
оранжевая, дымка за спиной синяя, и ни один градиент никем не задан.

## 4. Порядок разработки

Модули писались снизу вверх, с проверкой типов после каждого слоя.

1. **Каркас** — `package.json`, `tsconfig.json`, `vite.config.ts`, `index.html`.
2. **Ядро** — математика (reversed-Z проекции, фрустум по Гриббу-Хартманну,

## 5. Найденные и исправленные ошибки

Все они найдены не чтением кода, а инструментами. Порядок хронологический.

### 5.1 Отсутствие точности для sampler2DArray в вершинных шейдерах

Первый же запуск смоук-теста упал на компиляции `chunk.opaque:vs`. GLSL ES 3.00
задаёт точность по умолчанию для `float` и `int` в вершинной стадии, но **не**
для типов сэмплеров-массивов, 3D и теневых — их надо объявлять в каждой стадии,
где они упоминаются.

### 5.2 Ориентация текстур на половине граней блока

Найдено по контактному листу материалов (`materials.html`).

Мешер строит базис так, чтобы `u × v` равнялось нормали грани **и** все
компоненты были неотрицательными — иначе развёртка greedy-прохода
`origin + u*i + v*j` не работает. Из-за этого мировая вертикаль попадала на `u`
у граней `+X` и `−Z`, но на `v` у `−X` и `+Z`.

Последствие: травяная кромка, слои песчаника, ряды досок, фактура коры и рёбра
кактуса были повёрнуты на 90° на половине сторон каждого блока.

Исправление — таблица `FACE_SWAP_UV` и транспонирование тайловых координат для
двух граней.

### 5.3 «Провода» через всё небо

Самый эффектный баг. На скриншотах рассвета через всё небо тянулись тонкие
тёмные линии, сходящиеся в точку схода.

Причина: позиции вершин пишутся в `Uint16Array`. Крестовидное растение у края
секции с джиттером даёт координату около −1.3 в восьмых долях блока, что
заворачивается в 65534 и ставит вершину на 8192 блока от чанка. Квад
растягивается через полмира и рисуется как линия.

Исправление: `POSITION_BIAS` в один блок, вычитаемое в вершинном шейдере. Плюс
запас в 1 блок на ограничивающий объём секции, чтобы такая геометрия и
колыхание от ветра не отсекались фрустумом на краю экрана.

### 5.4 Цвета биомов: sRGB против линейного

Трава была вымыта почти в белый. Цвета биомов задавались так, как их читает
человек — в sRGB, — а использовались как линейное альбедо. sRGB 0.55 это
линейное 0.26, то есть яркость завышалась вдвое.

Атлас нельзя объявить sRGB-текстурой, потому что его четвёртый слой несёт
данные рельефа (высота, тип поверхности, свет), которые декодировать нельзя.
Поэтому преобразование делается в шейдере, в `sampleTintAtlas`.

### 5.5 Отсутствие автоэкспозиции

Полдень был пересвечен при экспозиции, при которой виден закат, и наоборот —
закат уходил в чистый чёрный. Физически корректная сцена без адаптации
неизбежно так себя ведёт: яркость неба меняется на два-три порядка.

Добавлена цепочка редукции яркости на GPU: сцена → 64×64 логарифм яркости →
16×16 → 4×4 → 1×1, затем адаптация в 1×1 текстуру с пинг-понгом между кадрами.
Всё на GPU, без чтения обратно и без остановки конвейера.

Адаптация асимметричная: глаз быстро темнеет при вспышке света и медленно
светлеет в темноте. Нижняя граница диапазона — то, что оставляет ночь ночью, а
не превращает её в пасмурный день.

### 5.6 Двойной учёт затухания солнца

Даже после автоэкспозиции закат оставался чёрным. Причина: интенсивность солнца
гасилась вручную по его высоте (`dayFactor`), хотя физическое затухание уже даёт
трансмиттанс — и даёт его **по каждой длине волны отдельно**, что и есть
причина красноты заката. Умножение одного на другое обнуляло сумерки.

Исправление: интенсивность не зависит от высоты вообще, а мягко гасится только
когда солнце достаточно далеко под горизонтом. Всё остальное делает физика.

### 5.7 Слишком плотный туман

С вершины горы вся долина внизу тонула в молоке. Аналитический интеграл
экспоненциального тумана по высоте при взгляде вниз растёт экспоненциально —
формула верна, но плотность и высота шкалы были подобраны для горизонтального
взгляда на уровне моря.

Плотность снижена втрое, спад по высоте сделан заметно мягче.

### 5.8 Шов на горизонте

Между дальним рельефом и небом шла жёсткая серая полоса: купол неба и туман
считали цвет ниже горизонта по-разному. Введена общая функция
`atmosphereColor(dir)`, которой пользуются оба.

### 5.9 Облака не рисовались вообще — две независимые причины

**Первая.** Композит облаков читал текстуру глубины, **прикреплённую к тому же
FBO**, в который рисовал. Это неопределённое поведение. Заменено на честный
depth-тест на дальней плоскости — тот же результат, одно сравнение вместо
выборки текстуры.

**Вторая.** В формуле плотности покрытие задавало нижнюю границу `remap`:

```glsl
density = remap(base, 1.0 - coverage, 1.0, 0.0, 1.0);
```

При среднем покрытии 0.2 это требовало от базовой формы значений выше 0.8,
которых сумма Ворли практически никогда не достигает. Небо оставалось пустым.
Отображение перецентрировано на запрошенное покрытие.

### 5.10 Наложенные поверхности воды

Самая дорогая ошибка проекта, и она же давала визуальный артефакт.

У воды отсекались только **боковые** грани между двумя блоками воды, а верхняя
— нет. В двадцатиблочном океане это двадцать наложенных полупрозрачных
поверхностей: они дрались за глубину, давали пилу на береговой линии и
двадцатикратный overdraw.

Проход воды: **107 мс → 5.5 мс**.

### 5.11 Ямки в снегу

Снежные биомы использовали снег как материал поверхности, а декоратор кладёт
слой снега только на колонки, которые снегом ещё не заканчиваются. Итог — поле
ямок в один блок вперемешку с ровными участками.

Исправление: снежные биомы больше не используют снег как поверхность, и слой
кладётся единообразно на все сухие колонки.

### 5.12 Отсечение передних граней в теневом проходе

Приём стандартный — для **замкнутых тел**: он сохраняет в карту дальнюю сторону
объекта и даёт смещение бесплатно. Но greedy-мешеный воксельный мир это
оболочка без внутренних граней, поэтому отсечение передних граней выбрасывало
ровно те поверхности, что отбрасывают тень.

### 5.13 Чтение неотрисованной карты теней

При выключенных тенях шейдер всё равно вызывал `sampleShadow`, который читал
текстуру, в которую в этом кадре никто не рисовал. Помимо произвольных тёмных
пятен это делало A/B-тест «с тенями / без теней» бессмысленным как диагностику.

### 5.14 Атлас биомов не перезаливался

При смене дальности прорисовки рендерер пересоздаёт тороидальный атлас, но
флаги «тайл уже загружен» в мире оставались выставленными — тинты и карта
размещения травы молча оставались пустыми. Добавлен `invalidateAtlases()`.

## 6. История оптимизации

Стартовая точка на UHD 620: низкий пресет 24 fps, средний 12, высокий 7,
ультра 2.5.

### 6.1 Сначала методика, потом оптимизация

Первые A/B-замеры дали противоречивую чушь:

```
no clouds      152.4 ms   медленнее базы на 98 мс
half res        69.4 ms   медленнее базы на 16 мс
rd 4           135.0 ms   медленнее базы на 81 мс
```

Отключение фичи не может замедлять кадр. Причина оказалась в **тепловом
троттлинге**: ноутбучный UHD 620 за 4+ минуты непрерывной нагрузки теряет около
трети производительности, а прогон шёл последовательно — база мерилась
холодной, остальные случаи всё горячее.

Это же означало, что и первая таблица по пресетам была перекошена: низкий
мерился холодным, ультра горячим.

Два вывода, оба зафиксированы в инструментах:

* **`scripts/breakdown.mjs`** — каждый случай обрамляется свежим замером базы, и
  результат считается относительно среднего двух соседних баз. Медленный
  тепловой дрейф сокращается полностью.
* **`scripts/gputime.mjs`** — GPU-миллисекунды по каждому проходу через
  `EXT_disjoint_timer_query_webgl2` плюс разбивка CPU по фазам цикла. Это
  основной инструмент: он не зависит ни от троттлинга, ни от квантования по
  vsync.

После исправления методики картина стала осмысленной:

```
no shadows    экономия 20.3 ms   38%
half res      экономия 10.3 ms   19%
no grass      экономия  5.2 ms    9%
no ssao       экономия  4.3 ms    8%
no taa        экономия  3.8 ms    7%
no clouds     экономия  0.1 ms    0%
rd 4          экономия -0.8 ms   -2%   ← в вершины не упираемся
```

### 6.2 Облака: аналитический шум → 3D-текстуры

Первая версия считала Ворли аналитически: 27 проверок ячеек на октаву, три
октавы на выборку, плюс марш к солнцу в шесть шагов на каждом из двадцати шагов
основного марша. Порядка **500 миллионов хеш-вычислений на кадр**.

Заменено на две запечённые 3D-текстуры (форма 64³ и детали 32³, разделение
shape/detail из системы Nubis студии Guerrilla). Каждая выборка плотности —
пара обращений к текстуре.

**~40 мс → 0.39 мс.**

Важная деталь: покрытие считается один раз на шаг марша и переиспользуется
маршем к солнцу, вместо пересчёта на каждом из его шагов.

### 6.3 Вода: отсечки по расстоянию

Экранные отражения это около 20 зависимых выборок текстуры на пиксель, а
детальные нормали — шесть вызовов fBm ради градиента. Когда океан занимал
пол-экрана, проход стоил 107 мс.

Сделано: SSR не трассируется дальше 52 блоков (дальняя вода отражает почти
только небо, а откат на небо и так есть), детальные нормали отключаются ветвью
за 56 блоками, шероховатость расширяется с расстоянием (штатное лекарство от
мерцания бликов), тени на воде не выбираются вдали, диск солнца в отражении
рисуется только вблизи, зенит неба берётся прямой выборкой LUT без `acos`.

### 6.4 Удаление depth prepass

Prepass существовал только чтобы дать SSAO буфер нормалей. Измерение показало:
7 мс GPU **плюс половина всех draw call в кадре** ради прохода, который сам
стоит 1.5 мс.

SSAO переписан так, что восстанавливает нормали из производных глубины и
работает **по кадру назад**: считается в конце кадра, потребляется следующим с
репроекцией через мировую позицию. Затенение низкочастотное и привязано к
мировым координатам, поэтому кадр задержки невидим.

Заодно убрано второе цветовое вложение основного кадрового буфера.

### 6.5 Листва

Изначально листва не отсекала грань с соседним блоком листвы — чтобы крона
читалась как объём. Цена: шестикратная геометрия, и кроны составляли больше
половины всех квадов в лесу.

Поскольку проход cutout рисуется двусторонним, взгляд сквозь просвет в ближней
оболочке всё равно показывает изнанку дальней — глубина сохраняется.

**705 тыс. квадов → 173 тыс.**

### 6.6 Ступенчатые каскады теней

Дальние каскады покрывают большую площадь и почти не меняются от кадра к кадру.
Каскад 0 обновляется каждый кадр, первый — раз в два, второй и третий — раз в
четыре. Каскад, который не перерисовывается, обязан сохранить **ровно ту
матрицу**, с которой была отрисована его глубина, иначе каждая выборка из него
попадёт не туда.

### 6.7 Бюджет выгрузки мешей

Шесть воркеров могут отдать десяток готовых секций в одном кадре, а каждая
выгрузка это синхронный `bufferData` в главном потоке. Отсюда рывки: медиана
56 fps при 1% low в 19.

Введён бюджет по времени (а не по количеству — секция бывает и в один квад, и в
двадцать тысяч), адаптивный: при длинной очереди больше, чтобы мир быстрее
проявлялся на старте, при короткой меньше, чтобы приходящий чанк не давал
видимой задержки.

**1% low: 19 → 28 fps.**

### 6.8 Итог

| | Было | Стало |
|---|---|---|
| Низкий, медиана | 24 fps | **57 fps** |
| Средний, медиана | 12 fps | **55 fps** |
| Средний, среднее | 10.5 fps | **36 fps** |
| Высокий, медиана | 7 fps | **28 fps** |
| Ультра, медиана | 2.5 fps | **12 fps** |

Качество при этом не снижалось — наоборот, по дороге облака впервые заработали
вообще.

Текущий профиль среднего пресета (28.8 мс на кадр): GPU 24.1 мс, CPU в
`render()` 22.9 мс. То есть **дальнейшая оптимизация шейдеров упрётся в
накладные расходы драйвера на draw call**, и следующий шаг — объединение секций
колонки в один буфер.

## 7. Анализ потолка: где предел и почему он не в стеке

Вопрос, который встал после первой играбельной версии: текущие ~30 fps — это
издержки этапа разработки или потолок браузерного стека? Стоит ли переписывать
движок на C++ и ставить компилятор?

Ответ получен тремя измерениями и он однозначный: **потолок не в стеке.**
Скрипты — `scripts/probe.mjs`, `scripts/resscale.mjs`, `scripts/resbreak.mjs`.

### 7.1 Это не накладные расходы на draw call

Гипотеза была такая: CPU тратит 23 мс на подачу ~330 вызовов отрисовки через
ANGLE→D3D11, и нативный движок это убрал бы. Проверка — менять дальность
прорисовки и смотреть, следует ли время CPU за числом вызовов:

```
rd  3  draws 365 (+124 тени)  CPU 28.73 ms  GPU 27.51 ms
rd  5  draws 354 (+736 тени)  CPU 29.33 ms  GPU 28.04 ms
rd  7  draws 360 (+ 27 тени)  CPU 28.49 ms  GPU 29.13 ms
rd  9  draws 560 (+ 27 тени)  CPU 28.40 ms  GPU 31.30 ms
```

Число вызовов выросло в полтора раза — **время CPU не изменилось вообще**. При
этом CPU ≈ GPU в каждой строке. Вывод: главный поток не подаёт команды, он
**блокируется в ожидании GPU**. Гипотеза опровергнута.

### 7.2 Это не только пиксели, и есть обрыв по vsync

Второй замер — менять только внутреннее разрешение, качество не трогать:

```
scale 1.00  1280x720   922k px   GPU 33.88 ms   медиана 32.1 fps
scale 0.85  1088x612   666k px   GPU 28.29 ms   медиана 32.1 fps
scale 0.70   896x504   452k px   GPU 26.15 ms   медиана 32.1 fps
scale 0.60   768x432   332k px   GPU 23.21 ms   медиана 32.1 fps
scale 0.50   640x360   230k px   GPU 24.29 ms   медиана 32.1 fps
```

Два факта. Первый: пикселей в четыре раза меньше, а GPU упал лишь с 34 до 24 мс
— значит большая часть кадра от разрешения не зависит.

Второй, важный для восприятия: **медиана приклеена к 32.1 fps во всех пяти
случаях.** Это vsync. Кадр не влезает в 16.7 мс, поэтому показывается через
одно обновление экрана — ровно 30 fps. Это **обрыв, а не плавная деградация**:
пока кадр 17 мс — 30 fps, как только 16 — сразу 60. Отсюда и субъективное
ощущение «тормозит» при формально неплохих цифрах.

### 7.3 Где кадр на самом деле

Третий замер разделяет каждый проход на зависящую и не зависящую от разрешения
часть (1280×720 против 640×360):

```
проход              1.00x   0.50x   не зависит   зависит
chunks opaque       12.55    9.21        9.21      3.34
shadow maps          2.70    2.56        2.56      0.14
water                5.15    2.29        2.29      2.86
grass                2.19    2.45        2.19      0.00
composite            1.16    1.06        1.06      0.10
ssao                 1.98    0.40        0.40      1.59
taa                  1.41    0.34        0.34      1.07
bloom                1.09    0.28        0.28      0.81
scene copy           1.35    0.27        0.27      1.07
прочее               1.28    0.86        0.64      0.75
──────────────────────────────────────────────────────
итого               30.97               19.24     11.73
```

**Неснижаемая часть — 19.2 мс при бюджете 60 Гц в 16.7 мс.** Это обработка
геометрии: около 1.1 млн вершин за кадр (чанки + трава + повторная отрисовка в
теневые карты). Никакое уменьшение разрешения её не трогает.

Отдельная находка: `chunks opaque` даже при 640×360 стоит 9.2 мс, то есть это
**вершинная** нагрузка. В вершинном шейдере чанков есть выборка из атласа
тинтов — это ~900 тысяч обращений к текстуре в вершинной стадии за кадр, и на
Intel это дорого. Кандидат на перенос во фрагментный шейдер.

`composite` не зависит от разрешения по построению: он всегда пишет в холст
полного размера, каким бы ни был внутренний буфер.

### 7.4 Почему переписывание на C++ не поможет

Узкое место — пропускная способность самого GPU по вершинам и пикселям. Шейдер
через ANGLE компилируется в тот же самый байткод D3D11, который выполнил бы
нативный движок, на тех же 24 исполнительных блоках. Эти 19.2 мс не изменятся
ни на миллисекунду от смены языка.

Нативный движок выигрывает там, где узкое место — подача команд драйверу
(тысячи вызовов) или логика на CPU. Измерено: подача не бутылочное горлышко
(7.1), а вся логика мира, рейкаст и сбор источников света вместе занимают
**0.25 мс на кадр**.

WebGPU на этой машине, кстати, доступен (адаптер Intel, архитектура gen-9,
устройство создаётся). Он дал бы compute shaders и render bundles, но нашему
узкому месту не помогает — это задел на будущее, а не лекарство.

### 7.5 Про сравнение с Left 4 Dead

L4D2 летает на этом же GPU, и это не противоречие, а подтверждение диагноза.
Две причины, обе — архитектура движка, а не язык:

* **Свет запечён в лайтмапы.** Пиксель стоит одну выборку текстуры, порядка
  30–50 операций. У нас полный PBR + шесть выборок теней + атмосфера, порядка
  тысячи. Это прямая цена той картинки, которая была в постановке задачи.
* **Precomputed Visibility.** Source заранее знает, что видно из какой комнаты,
  и отправляет на GPU долю уровня. У нас **нет ни LOD, ни occlusion culling** —
  мы честно рисуем 1.1 млн вершин каждый кадр, включая те, что за холмом.

То есть L4D2 обгоняет нас ровно тем, чего нам не хватает.

### 7.6 План до 60 fps, с оценками

| Что | Сейчас | Цель | Как |
|---|---|---|---|
| chunks opaque | 9.2 мс | ~4 мс | LOD дальних чанков; убрать выборку текстуры из вершинного шейдера |

### Что удалось установить про треугольники (эта сессия)

Добавлен отладочный режим 8 — заливка бакета сплошным цветом, ровно тот
инструмент, который прошлая сессия наметила как следующий шаг. Плюс
`debugview.mjs` научился кадрировать все каналы одинаковым прямоугольником.
Снято на сиде `424242`, полдень, `faceSun(2.2, -0.22)`:

* **Это непрозрачный бакет.** В режиме бакетов пиксели треугольников зелёные:
  ни вода, ни листва/растения, ни инстансированная трава к ним отношения не
  имеют. Три подозреваемых закрыты одним снимком.
* **Это боковые грани `+X`.** В канале нормалей треугольники розовые
  (нормаль ≈ `(1,0,0)`) на фоне бледно-зелёной горизонтальной поверхности.
  То есть шейдер получает нормаль боковой грани, а не «затеняет» верхнюю.
* **Геометрия под ними настоящая.** Дамп высот столбцов вокруг камеры
  показывает нормальную лестницу террас без одиночных шипов: песок и глина у
  воды, снег выше. То есть боковые грани там законно существуют — вопрос
  только в том, почему видна ровно половина каждого квада.
* **В канале вершинного AO та же область читается прямоугольниками**, без
  диагонали. Значит по диагонали различаются только плоские (`flat`)
  атрибуты — а они берутся из провоцирующей вершины, и у обоих треугольников
  квада она лежит внутри того же квада.

Отсюда следующий шаг для новой сессии: снять ту же область с трёх углов
наклона камеры. Если треугольники ведут себя как настоящая геометрия (растут и
становятся прямоугольными при взгляде сверху) — это корректно нарисованные
стенки террас, и «баг» сводится к тому, что вертикальная грань в полдень почти
не получает солнца; тогда лечится это не поиском ошибки, а мягким ambient'ом на
отвёрнутых гранях. Если форма не меняется — искать в мешере квад, у которого
одна из четырёх вершин уезжает.

## 10. Отладочное API

При запуске в `window.supergraph` кладётся объект, через который можно
управлять игрой без pointer lock — на нём построены все скрипты в `scripts/`, и
он же удобен из консоли браузера.

```js
supergraph.teleport(x, y, z)          // поставить игрока
supergraph.ground()                    // уронить на ближайшую твердь, вернуть y
supergraph.findViewpoint(radius)       // найти открытую видовую точку и встать
supergraph.look(yaw, pitch)            // повернуть камеру
supergraph.faceSun(offset, pitch)      // повернуть относительно азимута солнца:
                                       //   0 — на солнце, PI — от солнца

supergraph.setTime(t, freeze = true)   // 0..1; 0.25 рассвет, 0.5 полдень,
                                       //   0.72 золотой час, 0.76 сумерки
supergraph.setWeather(rain, snow = 0)  // 0..1

supergraph.setPreset('low'|'medium'|'high'|'ultra')
supergraph.setSetting(key, value)      // одна настройка, для A/B

supergraph.setDebugView(n)             // 0 обычный, 1 вершинный AO,
                                       //   2 небесный свет, 3 блочный свет,
                                       //   4 нормаль, 5 SSAO, 6 альбедо, 7 тинт,
                                       //   8 бакет (какой проход закрасил пиксель:
                                       //     зелёный opaque, жёлтый cutout,
                                       //     красный вода, синий translucent,
                                       //     розовый инстансированная трава),
                                       //   9 текстурный AO, 10 поле высот
supergraph.enableGpuProfiler(true)     // вернёт false, если драйвер не даёт
supergraph.gpuTimings()                // [{name, ms}], отсортировано
supergraph.cpuTimings()                // {world, render, pick, lights, hud}
supergraph.frameTimes()                // мс между кадрами
supergraph.resetFrameTimes()
supergraph.stats()                     // {world, render}
supergraph.gpu                         // строка драйвера
```

`?seed=N` в адресной строке фиксирует мир. Без него сид случайный, и **любое
сравнение двух прогонов бессмысленно** — точка обзора окажется другой, а
стоимость воды и листвы зависит от неё в разы.

## 11. Инварианты и ловушки

Список того, что легко сломать, не заметив. Каждый пункт — либо уже пойманный
баг, либо решение, у которого есть неочевидное следствие.

**Reversed-Z везде.** Ближняя плоскость → 1, бесконечность → 0, очистка нулём,
тест `GEQUAL`, у теней тоже. Любой новый проход обязан соблюдать это
соглашение, включая сравнение в сэмплере теней (`TEXTURE_COMPARE_FUNC` =
`GEQUAL`).

**Смещение позиции вершины.** Позиции хранятся в `Uint16` со смещением в один
блок (`POSITION_BIAS`), вычитаемым в `chunk_common.glsl`. Любой новый вершинный
шейдер, читающий `aPos`, обязан вычесть смещение. Геометрия, выходящая за
секцию больше чем на блок, снова начнёт заворачиваться.

**Четыре вершины на квад, всегда.** Индексный буфер общий и статичный. Любой
код, пишущий в `VertexWriter`, обязан писать вершины четвёрками, иначе
треугольники начнут собираться из вершин разных квадов.

**Нельзя читать текстуру, прикреплённую к текущему FBO.** Это уже один раз
съело облака целиком. Если проходу нужна глубина сцены, он либо читает копию
(`this.copy`), либо пользуется depth-тестом.

**Порядок стадий чанка нерушим.** `mesh` требует, чтобы окрестность 3×3 была
**освещена**, а не просто сгенерирована. Ослабление этого условия даёт швы на
границах чанков под навесами.

**Пропущенный каскад теней обязан сохранить свою матрицу.** Каскады
обновляются раз в 1/2/4 кадра; если пересчитать матрицу, не перерисовав
глубину, все выборки из этого каскада попадут не туда.

**SSAO работает по кадру назад.** Считается в конце кадра, потребляется
следующим с репроекцией через `uPrevViewProj`. Depth prepass удалён — не
возвращайте его, не измерив (раздел 6.4).

**Грани воды и листвы отсекаются с одинаковым соседом.** У воды это критично:
без этого в океане рисуется два десятка наложенных поверхностей (раздел 5.10).

**Тайловые UV транспонируются на гранях `+X` и `−Z`** (`FACE_SWAP_UV`). Любое
изменение базиса граней в мешере должно эту таблицу пересмотреть — **и вместе с
ней `FACE_TEX_U` / `FACE_UV_SIGN` в `chunk_common.glsl`**. Это две половины
одного соглашения: мешер решает, куда легли тайловые координаты, а шейдер
обязан строить по ним тангенциальный базис. Транспонирование ещё и зеркалит
хиральность UV, поэтому битангент на этих двух гранях — `−cross(N, T)`. Если
рельеф на них поедет не в ту сторону, смотреть сюда.

**Поле высот нормализуется на загрузке.** `normalizeHeight()` растягивает канал
высоты каждого материала на полный диапазон — иначе пак вроде Roundista, у
которого весь рельеф лежит в 245..255, даёт параллакс, которого не видно.
Следствие: относительная глубина рельефа между материалами не сохраняется, её
задаёт одна общая настройка `parallaxDepth`.

**Не редактируйте исходники во время замера.** Vite перезагружает страницу по
HMR, `window.supergraph` исчезает, и прогон падает посреди серии (или, хуже,
даёт бессмысленные числа). Замер идёт минутами — дождитесь его.

**Цвета биомов — в sRGB.** Декодируются в шейдере, а не текстурным форматом,
потому что четвёртый слой атласа несёт данные, а не цвет.

**Атлас биомов тороидальный.** Ширина — степень двойки, начала чанков кратны
32, поэтому тайл никогда не пересекает границу заворота. Не меняйте размер
чанка, не пересмотрев это. При смене дальности прорисовки атлас пересоздаётся и
мир обязан позвать `invalidateAtlases()`.

**Замеры на этом ноутбуке нужно нормировать.** Абсолютные FPS в
последовательном прогоне несравнимы из-за троттлинга. Пользуйтесь
`gputime.mjs` или чередующимся `breakdown.mjs`.

**Никогда не редактируйте исходники через PowerShell `Set-Content -Encoding
UTF8`.** Windows PowerShell 5.1 дописывает BOM, и GLSL от него падает с
`'?' : syntax error` в первой строке — ошибка выглядит как что угодно, кроме
своей настоящей причины. Если это всё же случилось, BOM снимается так:

```powershell
$enc = New-Object System.Text.UTF8Encoding($false)
[System.IO.File]::WriteAllText($path, $text, $enc)
```

**Текстуры пака грузятся асинхронно.** `initResources` и `createMaterials`
возвращают промисы, `main.ts` их дожидается. Если добавляете туда работу — не
теряйте `await`, иначе мир начнёт грузиться раньше материалов.

**Vite и воркеры при HMR.** После правки `chunkWorker.ts` или чего-то, что он
импортирует (мешер, генератор, свет, блоки), надёжнее перезагрузить страницу
целиком — горячая замена воркера не всегда подхватывается.

**SharedArrayBuffer требует COOP/COEP.** Заголовки прописаны в
`vite.config.ts` для `server` и `preview`. Если открыть `dist` статикой без
них, движок молча уйдёт на однопоточный путь и будет заметно медленнее
подгружать мир — это не баг, но при замерах об этом надо помнить.

### Итог второго этапа

Сделаны пункты 1 и 6, плюс две находки, вытекшие из замеров по ходу.

| Пресет | Было (медиана / среднее) | Стало |
|---|---|---|
| Низкий | 57 / 52 | **58 / 57** |
| Средний | 55 / 36 | **58 / 53** |
| Высокий | 28 / 25 | **55 / 33** |
| Ультра | 12 / 12 | **19 / 16** |

Средний пресет: 28.8 → **19.0 мс** на кадр. Обрыв по vsync пройден — кадр
больше не требует двух обновлений экрана.

Три правки, давшие это:

1. **LOD** — квадов 173k → 45.6k (пункт 1).
2. **Пропуск выборки теней на гранях, отвёрнутых от солнца** — 31.1 → 21.9 мс.
   Найдено потому, что LOD убрал геометрию, а проход подешевел лишь на
   четверть: значит цена пиксельная, и искать надо там.
3. **Копия кадра только когда в кадре есть вода** — 21.9 → 20.6 мс. Полноэкранный
   блит цвета и глубины нужен исключительно шейдеру воды.

Дальше на освободившийся бюджет лёг пункт 3 (параллакс). Что он стоит,
измерено чередующимся `breakdown.mjs` на высоком пресете:

| Случай | Дельта к базе |
|---|---|
| выключить параллакс целиком | −1.2 мс |
| 4 шага вместо 12 | −1.4 мс |
| 32 шага вместо 12 | +0.4 мс |
| дальность 8 блоков вместо 18 | −2.3 мс |
| включить самозатенение | **+2.2 мс** |

Читать так: **платит дальность, а не число шагов.** Затухание и снижение
шагов по углу срезают счётчик задолго до его номинала, поэтому «32 шага» стоят
столько же, сколько 12, а сокращение радиуса вдвое экономит больше, чем полное
отключение эффекта. Разброс базы за прогон — 35→40 мс из-за троттлинга, поэтому
точность здесь порядка ±1 мс и на знак строку «4 шага дешевле, чем выключить»
списывать не стоит. Честный вывод: **параллакс это 1–2 мс на высоком пресете и
около 0.3 мс на среднем**, а самозатенение — ещё столько же сверху, поэтому оно
включено только в «ультре».

### Пункт 1. LOD дальних чанков — СДЕЛАНО

> **Статус: реализовано.** Мешер параметризован по шагу прореживания
> (`LodStep` = 1 | 2 | 4), планировщик в `world.ts` выбирает уровень по
> расстоянию с гистерезисом, воркер получает шаг в задании.
>
> Результат на среднем пресете:
>
> | | Было | Стало |
> |---|---|---|
> | видимых квадов | 173k | **45.6k** |
> | `chunks opaque` | 9.02 мс | **6.78 мс** |
> | 1% low | 14.1 fps | **30.8 fps** |
> | ультра, квадов | 527k | **133k** |
>
> Решения, принятые по ходу:
>
> * **Представитель ячейки — самый верхний непрозрачный блок**, а не самый
>   частый. На расстоянии LOD глаз читает цвет поверхности сверху; выбор по
>   частоте покрасил бы травяные холмы цветом земли под ними.
> * **Ячейка считается сплошной по большинству** (более половины вокселей).
>   Это не даёт одиночному блоку раздуть целую ячейку и не наращивает дальние
>   силуэты.
> * **LOD-меши не несут вершинного AO и берут один уровень света на ячейку.**
>   Это не только дешевле считать — именно это позволяет greedy meshing
>   реально сливать квады вдали: ключ слияния схлопывается до «блок + тинт», и
>   склон холма становится десятком квадов вместо сотен. Отсюда падение в 3.8
>   раза, а не в 4 (шаг 2 даёт 4× по граням, но слияние даёт больше).
> * **Тайлинг текстуры считается по блокам, а не по ячейкам** (`w * step`),
>   иначе плотность текселей менялась бы на границе уровней.
> * Крестовидные растения и сбор источников света — только на полной
>   детализации: на дистанции LOD лезвие травы меньше пикселя.
> * Гистерезис 14%, переход не более чем на один уровень за раз.
>
> **Щелей на стыке уровней на практике не видно**, поэтому «юбки» не
> реализованы. Теоретически они возможны: колонка полной детализации отсекает
> грань по фактическому вокселю соседа, а сосед рисует агрегированную ячейку.
> Если щели проявятся — самое простое лекарство не юбки, а запрет отсечения
> пограничных граней со стороны более детальной колонки.
>
> **Главный вывод из замера:** квадов стало в 3.8 раза меньше, а `chunks
> opaque` подешевел лишь на 25%. Значит этот проход **больше не упирается в
> вершины — он упирается в пиксели**. Дальнейшее сокращение геометрии почти
> ничего не даст; следующий рычаг это стоимость фрагмента и внутреннее
> разрешение. Это меняет приоритет пункта 2 (occlusion culling): он снимет
> вершинную нагрузку, которой уже почти нет, а фрагментную и так снимает
> ранний тест глубины, потому что непрозрачная геометрия рисуется от ближней
> к дальней.
>
> **Проверка этого вывода сразу дала результат.** В шейдере чанков выборка
> теней выполнялась всегда, хотя грань, отвёрнутая от солнца, прямого света не
> получает вовсе — а это примерно половина видимой поверхности в любой момент.
> Один условный переход:
>
> ```glsl
> bool needsShadow = NoL > 0.0;   // для листвы NoL > -0.62:
>                                 // wrapped diffuse и просвет достают за терминатор
> ```
>
> | | До LOD | После LOD | + пропуск теней |
> |---|---|---|---|
> | кадр, средний пресет | 28.8 мс | 31.1 мс | **21.9 мс** |
> | fps | 34.7 | 32.0 | **45.6** |
> | `chunks opaque` | 9.02 мс | 6.78 мс | **5.29 мс** |
> | `shadow maps` | 1.84 мс | 2.06 мс | **1.45 мс** |
>
> Порог vsync пробит: кадр больше не всегда требует двух обновлений экрана.
>
> Что осталось до устойчивых 60 fps (бюджет 16.7 мс, сейчас 21.9): самый
> дорогой проход теперь **вода — 6.07 мс**, и она сильно зависит от того,
> сколько океана в кадре. Дальше `chunks opaque` 5.29 и `grass` 2.17. У травы
> есть очевидный резерв: две выборки текстуры на вершину, тинт можно перенести
> во фрагментный шейдер.

Ниже — исходный разбор задачи, он остаётся актуальным как справочник.


**Зачем.** Закрывает сразу две цели: снимает 5 мс с `chunks opaque` (самый
дорогой проход) и даёт дальность прорисовки уровня Distant Horizons. Одна
работа — два пункта из списка заказчика.

**Как.** За пределами N чанков мешить секции с шагом 2, дальше — 4 блока.
Мешер получает параметр `step`; при `step > 1` он читает воксели с
прореживанием и умножает размеры квадов. Свет и цвет биома усредняются по
объединяемому блоку.

Выбор блока-представителя важен: брать не «первый попавшийся», а
**самый частый непрозрачный** в группе 2×2×2, иначе дальний лес будет мигать
землёй между листвой.

**Щели на стыке уровней.** Соседние секции разного LOD дают разрыв в рельефе.
Дешёвое решение — «юбка» (skirt): по краям LOD-секции опустить крайние вершины
на `step` блоков вниз. Дырка закрывается стенкой того же материала, снизу её не
видно.

**Гистерезис обязателен.** Переключение LOD строго по расстоянию даёт мигание
на границе, когда игрок ходит туда-сюда. Переключать вверх на 1.15×
расстояния, вниз на 0.85×.

**Что менять:** `world/mesher.ts` (параметр шага), `world/world.ts`
(планировщик ставит задачи нужного уровня, перестраивает при смене),
`render/chunkGeometry.ts` (LOD-меш это ещё один вариант в `SectionRender`,
попадает в те же списки отрисовки и ту же сортировку по расстоянию).

**Ожидаемо:** дальность 16–32 чанка при стоимости не выше текущей на 7.

### Пункт 2. Occlusion culling

**Зачем.** Сейчас честно рисуется всё, что попало во фрустум, включая то, что
за холмом и за стеной пещеры. Это ровно то, что Source делает через
Precomputed Visibility и за счёт чего L4D2 летает.

**Как — и почему не Hi-Z.** Стандартный подход (иерархическая карта глубины
предыдущего кадра) требует либо чтения результата на CPU, то есть
синхронизации с GPU, либо GPU-driven рендеринга, которого в WebGL2 нет.

Для воксельного мира есть решение проще и лучше: у нас **уже есть двумерная
карта высот рельефа** (`solidHeightmap` по колонкам). Проверка «видна ли
секция» сводится к DDA-трассировке луча от камеры к её ближайшему углу по этой
карте: если рельеф между ними всюду выше линии взгляда — секция скрыта. Это
десятки шагов по массиву, целиком на CPU, без всякой синхронизации.

Для пещер этого мало (там перекрывает не рельеф), но снаружи, где основная
масса геометрии, работает.

**Что менять:** `render/chunkGeometry.ts` (`cull` получает дополнительную
проверку), `world/world.ts` (доступ к картам высот для трассировки).

**Подводный камень:** проверять не центр секции, а её ближайший угол, иначе
крупные секции у самой кромки холма будут исчезать.

### Пункт 3. Parallax occlusion mapping — СДЕЛАНО

> **Статус: реализовано,** вместе с самозатенением рельефа. Марш живёт в
> `chunk.frag.glsl` и включён только на непрозрачном бакете; настройки —
> `parallaxEnabled / parallaxSteps / parallaxDepth / parallaxDistance /
> parallaxShadows`, они же в панели графики.
>
> **Сначала пришлось починить тангенциальный базис.** Мешер транспонирует
> тайловые UV на гранях `+X` и `−Z` (`FACE_SWAP_UV`, баг 5.2), а тангент во
> фрагментный шейдер приходил из отдельной таблицы, которая этого не знала.
> Итог: на двух гранях из шести карта нормалей была зеркально отражена по
> диагонали — незаметно на процедурных материалах, но для параллакса это
> означало бы марш не в ту сторону. Таблица `FACE_TANGENT` заменена на
> `FACE_TEX_U` + `FACE_UV_SIGN`: тангент теперь **это ось U текстуры**, а знак
> несёт хиральность UV (транспонирование её зеркалит, поэтому на `+X` и `−Z`
> битангент это `−cross(N, T)`). Заодно ушёл Gram-Schmidt в шейдере: базис
> граней осевой, ортогонализировать нечего.
>
> **Главная находка — поле высот в паке почти плоское.** У Roundista **все**
> материалы лежат в диапазоне 245..255 из 0..255, то есть 4% глубины. Нормаль
> из такого поля выводится, а марш упирается в стенку толщиной в ничто: первый
> прогон дал разницу, которую видно только при попиксельном сравнении. Поэтому
> `normalizeHeight()` в `packLoader.ts` растягивает поле каждого материала на
> полный диапазон — с двумя предохранителями: поле с размахом меньше четырёх
> уровней это не сжатый рельеф, а пак, который высоту не рисовал вовсе (такие
> остаются плоскими), и усиление ограничено 24×, чтобы дизеринг не превратился
> в скалу. Процедурные материалы проходят ту же нормализацию: их высоты писались
> под вывод нормали, с амплитудой «на глаз» (для этого и существует таблица
> `NORMAL_STRENGTH`), и маршу нужна форма, а не эта амплитуда.
>
> После нормализации булыжник выпукло читается на дистанции руки — см.
> `scripts/pomtest.mjs`, он строит стенку и снимает три кадра.
>
> Решения по ходу:
>
> * **Только непрозрачный бакет.** Cutout это кресты растений и оболочки
>   листвы — двусторонние билборды, у которых рельефа нет; translucent это
>   стекло и лёд, плоские по построению.
> * **Выборка высоты через `textureLod`.** Цикл марша это неоднородное
>   ветвление, где производные не определены; уровень считается один раз из
>   `dFdx/dFdy` неискажённого UV — того же, что уже считался для альфа-теста.
> * **Затухание гасит глубину рельефа, а не выключает марш.** Шаги едут по той
>   же кривой, поэтому переход не видно: на границе дальности рельеф уже нулевой.
> * **Шагов больше на скользящем взгляде** (`mix(1.0, 0.45, NoV)`): луч проходит
>   по рельефу тем длиннее, чем острее угол, и редкие срезы дают лесенку.
> * **Тайловые UV — это блоки,** поэтому смещение UV и смещение в мире это одно
>   и то же число, а `parallaxDepth` читается прямо в блоках.
> * **Самозатенение** — отдельный марш к солнцу от точки попадания, 6 шагов,
>   только там, где каскады и так дали свет. Каскады разрешают метры, рельеф
>   внутри текселя может затенить себя только сам.
>
> **Заодно закрыт остаток пункта 6:** канал подповерхностного рассеяния
> подключён к листве (сила просвета теперь свойство материала, а не константа
> 0.3), а пористость из того же канала управляет тем, насколько материал темнеет
> под дождём — песок и камень пьют воду, металл и стекло только глянцевеют.
> Процедурные материалы получили таблицу `PROCEDURAL_SUBSURFACE`, чтобы путь без
> пака не потерял просвечивающую листву.
>
> **Что осталось из пункта 3:** мокрые отражения на суше (SSR для поверхностей с
> высокой влажностью). Не сделаны сознательно — это плюс к кадру там, где бюджет
> уже расписан под пункты 4 и 5.

Ниже — исходный разбор задачи, он остаётся актуальным как справочник.

**Зачем.** Самый заметный скачок в «объёмности блоков» — это то, что делает
`pegasus-4` и `screen-0` непохожими на плоские текстуры. Камешки булыжника
выступают, швы кирпича уходят вглубь, и всё это с самозатенением.

**У нас уже есть данные.** `render/textures.ts` считает поле высот для каждого
материала, чтобы вывести из него нормаль (`packSurface`), но саму высоту
выбрасывает. Её надо начать сохранять — и это тот же самый канал, который
приносит LabPBR (пункт 6), поэтому **пункты 3 и 6 делать одной задачей**.

**Алгоритм.** В `chunk.frag`, до выборки альбедо: перевести направление взгляда
в тангенциальное пространство (базис `tangentFrame` уже есть), идти по нему
шагами, сравнивая текущую высоту луча с картой высот, найти пересечение,
сместить UV. 8 шагов вблизи, 32 в режиме «красиво».

**Отсечка по расстоянию обязательна:** полностью выключать дальше ~12 блоков,
число шагов уменьшать плавно. Иначе это стоит не 2.5 мс, а 15.

**Силуэт остаётся плоским.** Настоящее смещение силуэта грани стоит дорого;
стандартный компромисс — объёмная поверхность внутри плоской грани. На
референсах этого не видно, потому что грани блоков и так прямые.

**Самозатенение** (тень от выступов на самих выступах) — отдельные 4–6 шагов к
солнцу, только вблизи. Именно оно даёт вид «настоящего рельефа», а не «рисунка
рельефа». Добавлять после базового POM и мерить отдельно.

**Мокрые отражения** (`glsl-shaders-mod-2`) — сюда же: SSR на половине
разрешения только для поверхностей с высокой влажностью, то есть только во
время дождя. Код трассировки уже написан в `water.frag.glsl`, его надо вынести
в библиотеку и переиспользовать.

**Что менять:** `render/shaders/chunk/chunk.frag.glsl`, `render/textures.ts`
(сохранять высоту), новая третья текстура-массив (см. пункт 6).

### Пункт 4. Плотность травы — СДЕЛАНО

> **Статус: реализовано.** Поле травы рисуется тремя концентрическими
> кольцами — по вызову на кольцо, — с плотностью 16 / 5 / 2 лезвия на блок при
> `grassDensity = 1`. Было 6 на блок равномерно по всему радиусу.
>
> | | Было | Стало |
> |---|---|---|
> | лезвий на блок вблизи | 6 | **16** |
> | лезвий на блок вдали | 6 | 2 |
> | инстансов, средний пресет | 31.1k | 29.3k |
> | проход `grass` | 2.1 мс | **2.1 мс** |
>
> То есть плотность у ног выросла в 2.7 раза, а кадр не подорожал вовсе.
> Бюджет второго этапа закладывал на это +2 мс — их не понадобилось.
>
> Как это устроено и почему переходы между кольцами не видно:
>
> * **Позиция лезвия — хеш от клетки и его номера.** Поэтому первые N лезвий
>   плотного кольца это буквально те же лезвия, на тех же местах, что и всё
>   содержимое разреженного кольца за ним. Через границу переходит не «другая
>   трава», а та же самая, просто без излишка.
> * **Излишек не исчезает, а гаснет** на внешней трети своего кольца
>   (`uCarryBlades` говорит шейдеру, сколько лезвий держит следующее кольцо).
> * **Размер лезвия — функция расстояния, а не кольца.** Иначе лезвие,
>   переходящее границу, скачком меняло бы ширину. К внешнему краю поля лезвие
>   в 2.1 раза шире и на четверть выше: их там вчетверо меньше, и каждое должно
>   закрывать больше земли.
> * **Проверка кольца идёт до всякой выборки текстуры.** Сетка квадратная,
>   кольцо круглое, поэтому пятая часть инстансов в каждом вызове существует
>   только чтобы быть отброшенной — и стоить она должна ровно одну вершинную
>   инвокацию.
>
> **Попутно исправлен баг ориентации.** Прежнее прореживание сравнивало
> `rnd2.x` с порогом, а этим же `rnd2.x` задавался угол поворота лезвия. То
> есть чем дальше от камеры, тем в более узкий сектор смотрели все выжившие
> лезвия. С кольцами прореживание по случайному числу исчезло, и угол снова
> распределён равномерно.
>
> **Что осталось:** вершинная стадия по-прежнему делает две выборки на вершину
> (карта поверхности и атлас тинтов), то есть семь раз на лезвие вместо одного.
> Перенос тинта во фрагментный шейдер, который предлагался ниже, **считать
> выигрышем нельзя**: близкое лезвие покрывает под сотню пикселей против семи
> вершин, так что это обмен семи выборок на сотню. Если возвращаться к этому,
> то правильный ход — убрать лишние инстансы (квадратные кольца по метрике
> Чебышёва вместо круглых дают точную кольцевую индексацию и снимают ту самую
> пятую часть), а не переносить выборку вниз по конвейеру.

Ниже — исходный разбор задачи, он остаётся актуальным как справочник.

**Зачем.** На референсе `детализация поверхности природы` трава — сплошной
ковёр, у нас редкие кустики. Нужно ~12–16 лезвий на блок вблизи против
нынешних 6–8.

**Ключ — не просто поднять число, а сделать LOD травы.** Сейчас плотность
одинакова по всему радиусу и прореживается только вероятностно
(`grass.vert.glsl`). Надо кольцами: вблизи 16 на блок, в среднем кольце 4, в
дальнем 1, за ним — переход в текстуру травы на самой земле.

**Заодно убрать выборки текстуры из вершинного шейдера.** Каждый инстанс
делает две: `texelFetch` карты поверхности и `texture` атласа тинтов. При 30
тысячах инстансов по 7 вершин это 420 тысяч обращений в вершинной стадии. Тинт
можно перенести во фрагментный шейдер, карту поверхности оставить (без неё не
разместить лезвие).

**Что менять:** `render/shaders/grass/grass.vert.glsl` (кольца, перенос тинта),
`render/renderer.ts` (число инстансов на кольцо).

### Пункт 5. Воксельное глобальное освещение

**Зачем.** Это приближение к `ptgi2-8`: красная стена подсвечивает пол красным,
листва отбрасывает зелёный отсвет, в тени появляется объём вместо плоской
заливки ambient'ом.

**Почему это наш козырь.** У обычного движка нет воксельной структуры мира и
приходится строить её отдельно (voxel cone tracing). **У нас мир и так
воксельный** — структура уже есть, причём в разделяемой памяти, доступная
воркерам.

**Как.** Трёхмерная сетка освещённости вокруг игрока, один тексель на 4×4×4
блока. Например 64×48×64 текселя покрывают 256×192×256 блоков. RGB = приходящая
непрямая освещённость.

Заполнение — в воркере, инкрементально, по той же схеме, что уже написана в
`world/lighting.ts`: это флуд-филл, только с цветом и с умножением на альбедо
блока-источника. Небесный свет у нас уже посчитан, он и есть первичный источник.

Чтение — **одна трилинейная выборка `sampler3D` на пиксель**, добавляется к
ambient-члену в `chunk.frag`. Тороидальная адресация, как у атласа тинтов, чтобы
сетка ездила за игроком без перезаливки.

**Подводный камень:** утечка света сквозь тонкие стены — типовая проблема таких
сеток. Смягчается смещением точки выборки на полтекселя по нормали поверхности.

**Стоимость:** GPU ~1.5 мс, CPU амортизировано по воркерам. Память: 64×48×64
RGBA8 = 786 КБ.

>   одного массива текстур нельзя, а уменьшать авторскую текстуру ради ползунка
>   значит выбрасывать ту самую детализацию, ради которой пак и грузили.
>
> Осталось из этого пункта: подключить канал подповерхностного рассеяния к

Ниже — исходный разбор формата, он остаётся актуальным как справочник.


**Зачем.** Наши процедурные текстуры дают бесшовность, любое разрешение и ноль
веса, но художественную осмысленность (скол именно там, где он логичен;
кирпич с характером) процедурная генерация приближает, а не воспроизводит.
Если нужен вид Pegasus или Roundista — правильный путь не улучшать генератор
бесконечно, а научиться читать готовые паки.

**Пак уже в репозитории:** `Roundista 128x R32.zip`, 11.9 МБ, 128×128 RGBA,
2349 файлов текстур блоков.

**Формат LabPBR 1.3 — что в каких каналах:**

| Файл | Канал | Смысл |
|---|---|---|
| `foo.png` | RGB + A | альбедо и прозрачность |
| `foo_n.png` | R, G | нормаль XY (Z восстанавливается) |
| | B | ambient occlusion |
| | **A** | **карта высот для POM** (0 — дно, 255 — поверхность) |
| `foo_s.png` | R | perceptual smoothness |
| | G | F0 / металличность (0–229 = F0, 230–255 = индекс металла) |
| | B | пористость (0–64) или подповерхностное рассеяние (65–255) |
| | A | свечение (0–254, значение 255 = нет свечения) |

То есть пак несёт ровно те данные, которых нам не хватает: высоту для POM,
F0 вместо предположения 0.04, свечение и подповерхностное рассеяние для листвы.

**Покрытие проверено:** 44 из 46 наших материалов в паке есть. Отсутствуют
`water` и `lava` — паки их обычно не трогают, потому что вода рисуется
шейдером. У нас так же, оставляем процедурными.

**Соответствие имён** (наше → в паке):

```
grass_top       → grass_block_top      oak_log_side    → oak_log
grass_side      → grass_block_side     birch_log_side  → birch_log
sandstone_side  → sandstone            spruce_log_side → spruce_log
flower_red      → poppy                tall_grass      → tall_grass_top
flower_yellow   → dandelion            flower_blue     → cornflower
```

Остальные совпадают дословно.

**Что менять.** Нужна **третья текстура-массив** `material`: высота, F0,
свечение, SSS. Она же требуется для POM (пункт 3) — поэтому пункты 3 и 6
делаются вместе.

`render/textures.ts` получает второй источник данных: загрузчик пака рядом с
процедурным генератором. Процедурный остаётся как запасной вариант, для воды и
лавы, и для случая, когда пак не подключён.

**Загрузка zip в браузере** потребовала бы библиотеку. Проще — распаковать
нужные ~132 файла (44 материала × 3) один раз скриптом в `public/pack/` и
грузить обычными запросами. Скрипт распаковки заодно проверит покрытие и
сообщит, чего в паке нет.

**Память:** 44 материала × 128² × 3 текстуры × 4 байта ≈ 8.6 МБ. Незаметно.

**Подводный камень:** LabPBR-нормали хранят Z неявно и в разных паках
встречается разное соглашение по направлению Y (DirectX против OpenGL). Если
рельеф выглядит вывернутым наизнанку — инвертировать зелёный канал.

## 13. Звук

Единственная система, у которой два источника данных не по историческим
причинам, а по устройству — как и материалы: **сэмплы там, где запись лучше
синтеза, и синтез там, где записи не бывает.**

### Откуда берутся сэмплы

`scripts/extract-sounds.mjs` достаёт их из локально установленного Minecraft.
Игра хранит ассеты по содержимому: `assets/indexes/<N>.json` сопоставляет имя
(`minecraft/sounds/step/grass1.ogg`) хешу SHA-1, а сам файл лежит в
`assets/objects/<первые два символа хеша>/<хеш>` без расширения. Скрипт идёт по
индексу, копирует нужные группы в `public/sounds/` и пишет манифест с числом
вариантов в каждой.

```bash
node scripts/extract-sounds.mjs                      # найдёт %APPDATA%\.minecraft сам
node scripts/extract-sounds.mjs "D:\games\.minecraft" public/sounds
```

Берутся 28 групп, 119 файлов, 2.1 МБ: шаги и разрушение по восьми материалам,
дождь, гром, пещерный эмбиент, стекло, всплески. Не берутся музыка и 776
звуков мобов — именно они делают полный набор трёхсотмегабайтным.

**`public/sounds/` в `.gitignore`.** Это, в отличие от текстурного пака,
контент самой Mojang, поэтому он остаётся на машине, где его извлекли:
извлекатель — часть проекта, содержимое — нет. Без него движок звучит
синтезом, а не молчит.

### Что синтезируется

* **Ветер.** Записи нужной длины не бывает, а главное — он должен следовать
  ровно тому значению порыва, которое в этот же кадр гнёт траву. Это
  двухсекундная петля коричневого шума (белый шум, проинтегрированный: наклон
  −6 дБ на октаву — разница между ветром и эфирным шипением) через
  низкочастотный фильтр, у которого частота и громкость едут за `weather.wind`.
* **Дождь** — та же петля через высокочастотный фильтр, как подложка под
  записанные слои. Чем сильнее дождь, тем ниже срез: морось это шипение,
  ливень имеет тело.
* **Шаги и удары, когда сэмплов нет.** Полосовой всплеск шума с быстрой атакой
  и коротким хвостом: ухо читает материал по центральной частоте и длине
  затухания, а не по форме волны. Таблица `SYNTH` в `audio.ts` — по строке на
  материал.

### Что чем управляет

Ни одного нового запроса к миру: всё берётся из того, что движок и так считает.

| Звук | Источник |
|---|---|
| материал шага | блок под ногами → `BLOCK_SOUND` |
| мокрая трава | `weather.wetness` — то же значение, что темнит землю в шейдере |
| ветер | `weather.wind` — то же, что гнёт траву |
| дождь | `weather.rain` |
| пещерный эмбиент | запечённый небесный свет на уровне головы |
| глухота под водой | блок на позиции камеры |

### Инварианты

**Контекст стартует только из жеста.** Браузер не даст завести `AudioContext`
без клика, и единственный гарантированный клик в игре — кнопка «Играть».

**Группа загружается лениво и никогда не ожидается.** Шаг, который случился
раньше, чем догрузились его сэмплы, просто пропускается — следующий будет
через шаг. Блокировать кадр ради декодирования хуже, чем пропустить шаг.

**Пауза усыпляет контекст.** Эмбиент едет за погодой покадрово, а на паузе
кадров нет: без `suspend()` ветер завис бы на той громкости, что была в момент
Escape.

### Проверка

```bash
node scripts/audiocheck.mjs
```

Звук — единственная подсистема, которую не проверить скриншотом, а смоук-тест
до него не доходит: он водит игру через отладочный хендл и никогда не нажимает
«Играть». Этот скрипт нажимает, проигрывает по звуку каждого типа и печатает,
какие группы реально декодировались. Пустой список при `сэмплы: да` — значит
файлы запрошены и не получены.

## 14. Ответ на исходный вопрос

Да, сделать можно, и предположение заказчика подтвердилось: **шейдер-паки
дороги не потому, что это шейдеры, а потому что они пристроены снаружи к
движку, который о них не знает.**

Конкретное подтверждение из этого проекта: физически корректное небо с реальным
рэлеевским и ми-рассеянием стоит **0.23 мс на кадр** — потому что оно считается
один раз в таблицу 192×108, а не на каждый пиксель. Объёмные облака с маршем
лучей стоят **0.39 мс** — потому что шум запечён в текстуру, а интегрирование
энергосохраняющее. Каскадные тени с мягким фильтром стоят **1.84 мс**. Всё это
на графике 2017 года, встроенной в мобильный процессор с общей памятью.

Цена такого подхода — всё нужно спроектировать заранее и внутрь: формат вершины
под конкретный пайплайн, порядок проходов, атлас данных для растительности,
разделение статических и покадровых таблиц. Пристроить это снаружи к чужому
движку так же дёшево нельзя.
